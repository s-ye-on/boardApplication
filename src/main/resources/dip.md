## dip(의존성 역전의 원칙)
- "고수준 모듈은 저수준 모듈에 의존하면 안된다. 둘다 추상화에 의존해야 한다)
- 고수준이 저수준을 바라보면 안되니까 중간에 인터페이스르 둔다! -> 이건 오해
- 인터페이스가 누구의 것인가가 더 중요함
- 즉 인터페이스는 고수준이 소유해야함 (고수준의 정책을 저수준이 따라오게 만드는 것)
- controller = presentation(고수준)
- BoardServicePort = application(고수준 정책)
- BoardService = infra(저수준 구현)
- dip 핵심은 고수준의 정책이 인터페이스를 정의하고, 저수준이 그걸 구현하도록 만드는 것
- 단순히 인터페이스를 끼워넣는다고 DIP가 아니다.

## dip 원문 개념
- "고수준 모듈이 저수준 모듈에 의존해서는 안된다. 둘 다 추상화(인터페이스)에 의존해야 한다"
- 멘토님이 말한 "유연한 설계가 안될거야" : 지금 구조에서는 dip가 완전히 적용되지 않아서 진짜 유연하지 않을 수 있다는 의미
- Controller가 ServicePort인터페이스를 바라보더라도, 그 인터페이스가 BoardService에 너무 구체적으로 종속되어 있으면 결국 바ㄱ꾸기 어려움

- dip는 원래 이렇게 설계되어야 함
- Controller가 "나는 이런 기능이 필요해" 라는 요구 사항을 인터페이스로 정의
- Service가 "그 요구 사항을 내가 구현해줄게" 라고 의존성을 역전 시켜야함

## 현재
- dip 는 예를 들어 결제 방식이 여러개여서 나중에 결제 방식을 추가했을 때
- 코드 전체를 수정해야할 경우 인터페이스를 둬서 느슨하게 결합함
- 그런데 지금 BoardService의 boardCreate같은 기능은 한 가지만 존재하고
- 당장 바꿀 가능성이 없음 
- 굳이 BoardUseCase로 분리할 필요 없음
- 허나 순환참조 문제는 있으니 commonService로 빼서 각 서비스가 그거 참조
- 두 서비스가 직접 참조하지 않도록 


- 단순 기능이라면 Controller -> Service 직통 가능
- 확장 가능성이 있는 기능 -> UseCase + Service 

## 순환 참조 문제
- 가능하면 서비스 책임 분리
- 어쩔 수 없으면 @Lazy 필드 주입
- DIP로 인터페이스 분리도 방법이지만 단순 기능에는 과도
